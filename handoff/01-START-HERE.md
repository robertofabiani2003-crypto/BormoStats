# Доработки BormoStats: пакет для ревью

Дата: 29 октября 2026 года. Это описание локальной адаптации публичного проекта под магазин SVOYO, а не описание авторства исходного BormoStats.

## Что передать разработчику

Передайте весь ZIP. Начать следует с этого документа, затем прочитать `03-REVIEW-FINDINGS.md`, `02-FILE-MAP.md` и `04-VERIFICATION.md`. В `changed-files/` лежат точные копии всех 101 изменённого/добавленного исходного файла и прежних пояснений. `changes.patch` содержит изменения, включая новые файлы. `inventory.json` содержит размеры и SHA-256 каждого файла.

В архив не входят .env, LOGIN.local.txt, сертификаты, Docker volumes, резервные копии, node_modules и каталог outputs. В outputs обнаружено 30 неотслеживаемых файлов результатов: выгрузки, Excel, изображения и JSON. Они не считаются исходным кодом и не передаются. Исходные пояснения внутри changed-files содержат названия магазина, артикулы и примеры финансовых сумм; это часть существующей документации.

## Где проходит граница изменений

Локальный HEAD, main и сохранённый origin/main указывают на 282a1e0. Все обнаруженные доработки находятся в рабочей папке вне коммитов: 41 изменённый отслеживаемый файл и 60 новых исходных файлов/пояснений. Поэтому Git позволяет точно показать итоговую разницу с этой базой, но не позволяет восстановить порядок отдельных локальных доработок, их автора или промежуточные решения. Последние коммиты исходного проекта не приписываются владельцу этой установки. Обновление удалённого репозитория не выполнялось; свежесть origin/main в интернете не утверждается.

Рабочая установка остаётся в C:/dev/BormoStats на ветке codex/report-sync-daily. Пакет подготовлен в отдельном worktree C:/dev/BormoStats-review на ветке codex/customization-review от той же базы. Прикладной код не исправлялся, изменения не коммитились и не отправлялись на GitHub.

## Что поменялось для пользователя

### 1. Локальная установка Windows и одна площадка

Добавлены Start-BormoStats.ps1, Stop-BormoStats.ps1, compose.local.yaml и инструкция LOCAL-SETUP.md. Интерфейс доступен через локальные порты 18080/18443. Конфигурация подставляет несколько файлов backend и собранный frontend с диска. Проверка настроек допускает одну полностью настроенную пару Ozon или WB вместо обязательного наличия обеих площадок. Файл входа исключён из Git.

### 2. Прибыль, налог и расходы

Месячный P&L расширен налогом и корректировкой потоков финансирования. Добавлен дневной P&L, который используется главной страницей и страницей прибыли. Реклама Ozon берётся из удержаний финансового баланса: Performance-статистика используется для аналитики, а не повторного вычитания того же расхода.

Применённое правило налога — настройка пользователя, обычно 8%, а не универсальное правило для всех установок. Закрытый отчёт о реализации даёт месячную базу. При отсутствии полного покрытия код рассчитывает предварительную базу по ценам покупателя за вычетом возвратов. Дневной налог распределяется из месячной суммы с сохранением копеек. Флаг PNL_REALIZATION_TAX_ENABLED позволяет выключить налоговую поправку. Актуальную бизнес-корректность этих правил должен подтвердить владелец расчётов вместе с разработчиком.

Добавлена дата внешнего расхода и форма ввода. Расход с датой целиком относится к этому дню. Старый расход без даты распределяется поровну по календарным дням месяца. Общие расходы организации остаются общими даже при фильтре отдельного кабинета; интерфейс сообщает об этом.

Затронуты backend/app/services/pnl_service.py, новый daily_pnl_service.py, модели и API pnl.py, SQL месячной витрины, страницы Dashboard/PnL и миграция 0045. Для ежедневного отчёта основной расчёт: начислено с корректировками − себестоимость − внешние расходы − налог.

### 3. Экономика артикулов

Добавлен раздел /economics и его API. Начисления разбираются по SKU, выделяются виды удержаний, реклама привязывается по отчётам SKU. Расходы без подтверждённого артикула остаются в отдельной строке. Есть компактные/расширенные столбцы, фотографии, ABC по трём показателям и экспорт Excel. Самовыкупы и отдельный НДС пока не реализованы как полноценные показатели.

Основные файлы: common/article_economics.py, backend/app/services/article_economics_service.py, frontend/src/pages/Economics.jsx и economicsColumns.js. Резервные фотографии в economics_reference_images.json привязаны к ассортименту конкретного магазина.

### 4. Выкупы СНГ и реклама по SKU

Добавлены отдельные источники реализации, выкупов СНГ, рекламы по SKU и истории кампаний. Для СНГ реализовано исключение пересечений с обычными продажами. Рекламные UUID и результаты хранятся, чтобы повторно использовать незавершённые отчёты и получать исправления. Исчезнувшие из исправленного отчёта строки обнуляются новой версией. Основные файлы: collectors/ozon, workers/app/tasks/ozon_collect.py, common/ozon_buyouts.py, ozon_cis_service.py; миграции 0039–0042 и 0044.

### 5. Отдельная воронка Ozon

Добавлен импорт дневного Excel-отчёта в собственную таблицу, API и отдельный интерфейс. Данные импорта объединяются с отправлениями, финансовыми выкупами/возвратами, рекламой и историческими остатками. Различаются день заказа и день финансового события. Используются история SKU для прогнозов и метаданные для классификации рекламы. Основные файлы: backend/app/api/v1/funnel.py, common/funnel_economics.py, frontend/src/pages/OzonFunnel.jsx, ozonFunnel*.js; миграции 0043–0044.

### 6. Выбор периода, остатки и баланс

Новый календарь поддерживает готовые периоды и ручной выбор. Остатки и баланс запрашиваются на выбранную дату, остатки получили денежную оценку себестоимости. Добавлены подписи, экспорт и проверки. Исторические данные доступны только там, где сохранились снимки; новый календарь сам историю не создаёт.

### 7. Единый сбор аналитики 

Независимые таймеры сбора и пересчёта заменены единым последовательным циклом в 06:00 при московской настройке времени. Порядок: источники → staging → витрины → контроль качества → рекомендации. Есть общая блокировка и контрольные точки Redis на 7 дней, до 5 повторов с паузой 5 минут. Завершённый цикл за те же сутки повторно не получает отчёты. Пересчитывается окно 90 дней; у отдельных источников свои окна. Отзывы, правила, обслуживание и другие служебные таймеры остаются.

Дополнительно исправлены временные отметки, обновление поздних статусов отправлений, окна рекламы и сохранение истории планирования поставок. Свежесть интерфейса/мониторинга приведена к ежедневному циклу. Основные файлы: workers/app/tasks/reports.py, beat_schedule.py, tasks/marts.py, utils/watermarks.py, common/celery_config.py и правила Prometheus.

## Как разработчику восстановить разницу

В отдельном чистом клоне исходного репозитория перейти на коммит из BASE.txt, создать ветку и выполнить:

```text
git apply --check /path/to/handoff/changes.patch
git apply /path/to/handoff/changes.patch
```

Это восстановит отслеживаемые изменения и новые файлы. Файлы не будут автоматически закоммичены. Для проверки точности можно сравнить SHA-256 с inventory.json; Git может нормализовать окончания строк, поэтому бинарные хеши патча и точных копий могут различаться при совпадении текста. Перед запуском нужна отдельная тестовая конфигурация и применение миграций, а не копирование рабочего .env.

## Предлагаемый порядок ревью и доработки

1. Развернуть чистое тестовое окружение Python 3.14 по зависимостям исходного проекта и прогнать CI.
2. Исправить конкретные замечания из 03-REVIEW-FINDINGS.md: миграции, налоговые статусы, себестоимость и обновление производных показателей.
3. Сверить один закрытый месяц и несколько дней: начисления, реклама, возвраты, СНГ, себестоимость, внешние расходы и налог на всех трёх экранах.
4. Проверить отдельный кабинет и несколько кабинетов/организаций, роли чтения/записи и повторный импорт.
5. Проверить чистую сборку Docker без локальных bind-mount и переносимость конфигурации.
6. После исправлений разделить доработки на понятные коммиты: запуск; источники/миграции; прибыль; экономика; воронка; календарь; ежедневный цикл. Порядок уточнить по зависимостям. Текущий пакет фиксирует результат, а не подменяет его вымышленной историей коммитов.
