# Замечания для разработчика

Это предварительное ревью локального кода. Ниже явно разделены наблюдаемые дефекты, ограничения и гипотезы; полноценное тестирование backend и сверка с рабочей базой не проводились. Работающее приложение не исправлялось.

## Высокий приоритет

**R1. Отсутствует обязательный откат миграции 0044 — подтверждено по файлам и правилу CI.** Есть warehouse/migrations/0044_ozon_campaign_metadata.sql, но нет одноимённого файла в rollbacks. Функция verify_manifest в warehouse/apply_migrations.py требует откаты начиная с 0005; CI запускает verify. При установленном окружении эта проверка должна отклонить набор миграций. Добавить согласованный rollback и проверить manifest. Не запускать откат на рабочей базе ради проверки.

**R2. Главная может называть прибыль «после налогов», когда налог отключён — подтверждено по коду.** В frontend/src/pages/Dashboard.jsx `calculated` определяется только наличием строк дневного API. Этот API создаёт строки календаря и при отсутствии финансовых данных, а при выключенном налоге возвращает tax_status=disabled и tax=0. Заголовок карточки остаётся «Чистая прибыль после налогов». Нужны явные состояния: нет данных / до налога / налог оценён / налог подтверждён. Проверить пустую базу и выключенный флаг.

**R3. Отсутствующая себестоимость может завышать показываемую прибыль — подтверждённый путь, полнота последствий требует теста.** В daily_pnl_service.py отсутствующая себестоимость заменяется нулём и помечается missing_costs; Dashboard выводит предупреждение, но всё равно показывает числовую прибыль. В ozon_cis_service.py fallback `costs.get(sku, Decimal(0))` для добавленных выкупов не формирует такой счётчик. В экономике артикулов отсутствие себестоимости обрабатывается иначе — cogs=None. Нужна единая политика неполноты и тест случая «есть продажа СНГ, нет себестоимости».

## Средний приоритет

**R4. После корректировок месячной прибыли не обновляется margin_pct — подтверждено по коду.** Методы _apply_financing и _apply_cis в pnl_service.py меняют суммы выручки/себестоимости/прибыли, но оставляют процент из исходной витрины. Страница PnL использует margin_pct. Пересчитать производные показатели после корректировок, закрепив определение маржи и порядок расчёта.

**R5. Статус налога экономики может не совпадать с фактически подставленной суммой — подтверждённая рассогласованность источников статуса.** article_economics_service.py устанавливает tax_estimate из собственных report_bases, затем заменяет сумму налога значением DailyPnlService без пересчёта этого флага. DailyPnlService, в свою очередь, может получить estimated из месячного P&L при неполном покрытии баланса даже при наличии реализации. Нужен сценарий «реализация есть, финансовые дни месяца неполные» и единый статус на всех экранах.

**R6. Нужна проверка нескольких кабинетов — гипотеза риска.** ArticleEconomicsService объединяет записи нескольких account_id в один AccrualEconomics, карты товаров и себестоимости использует по SKU. В P&L налог ограничен PNL_TAX_ACCOUNT_ID, а экономика включает налог по организации. Проверить одинаковые SKU/номера отправлений в разных кабинетах и выбор нескольких кабинетов. Не считать корректность для одного SVOYO доказательством корректности многопользовательского режима.

**R7. Документация описывает разные версии поведения — подтверждено.** PNL-TAX-ROLLBACK.md обещает отсутствие прибыли до получения реализации и отдельный запуск 06:15; текущий код рассчитывает оценку и использует единый цикл 06:00. ARTICLE-ECONOMICS.md описывает рекламу раз в 6 часов, а также отсутствие изменений прежнего P&L; текущий diff меняет P&L и расписание. LOCAL-SETUP.md говорит о 38 применённых миграциях, тогда как в исходниках добавлены 0039–0045; состояние реальной базы не проверялось. Эти документы сохранены как исторические материалы, а не как актуальная инструкция. Свести правила в один действующий документ.

**R8. Локальный способ запуска может скрывать проблемы чистой сборки — ограничение.** compose.local.yaml монтирует dist и несколько Python-файлов поверх образа, Start-BormoStats.ps1 запускает up -d без --build, путь к Docker задан под Windows. Проверить результат после git apply и сборки чистых образов. Пересборка существующей рабочей установки в ходе этого аудита не запускалась.

**R9. Новые JS unit-тесты не подключены к CI — подтверждено конфигурацией.** В package.json нет команды для frontend/src/utils/*.test.mjs, а frontend job CI запускает build, тесты расширения и Playwright. Добавить запуск выбранных unit-тестов. При этом тесты dashboardProfit проверяют вспомогательный модуль, который текущий Dashboard уже не использует для карточки: они не покрывают R2.

## Отдельно согласовать бизнес-правила

- Исключение всей категории loans_and_factoring из расходов: подтвердить, нет ли в ней процентов/комиссий помимо тела долга. Тест проверяет арифметику корректировки, а не экономический состав категории.
- При фильтре одного кабинета общие расходы организации учитываются целиком. Это явно отражено в примечаниях API, но пользователь должен понимать результат.
- В P&L/остатках нулевая себестоимость приравнивается к отсутствующей; экономика артикулов различает ноль и отсутствие.
- Распределение месячного налога по подписанной дневной базе, дни с возвратами и нулевая суммарная база требуют контрольных примеров.
- Ежедневный цикл обновляет аналитику один раз в сутки. Ручная дозагрузка и независимые служебные задачи требуют проверки совместных блокировок и восстановления после сбоя Redis.
- Новые API должны пройти общие проверки прав, ограничений диапазона, пагинации, нагрузки и разграничения организаций. Наличие auth-зависимости само по себе не заменяет такие проверки.
